# Shape Quest — 背景影片統一美術與影片生成規格

版本：1.0  
日期：2026-10-31  
狀態：Grilling 完成，等待 Level 1 技術驗證  
適用範圍：Level 1～5、Boss Level

---

## 1. 專案定位

### 1.1 目標

為兒童體感跑酷遊戲 Shape Quest（奇形狀）建立一致、可擴充、可循環播放的動態背景影片系統。

影片由 Google Flow 等生成工具製作，遊戲以 HTML5 Video 播放背景，再使用 Canvas / WebGL 即時繪製障礙物與互動特效。

遊戲須支援智慧隨機障礙、動態難度與 MediaPipe Pose Landmarker 動作辨識，不依賴影片內建的固定事件時間。

### 1.2 核心原則 — CONFIRMED

1. 背景影片只負責世界環境和前進視覺。
2. 所有需要玩家反應的障礙物均由遊戲程式即時生成。
3. 不在背景影片內預先安排碰撞、動作提示或遊戲事件。
4. 遊戲時間軸是障礙物運動與動作判定的權威來源。
5. 背景影片與遊戲邏輯彼此解耦。
6. 影片可以循環、替換、擴充，不影響關卡玩法。
7. 影片靜音，音樂與音效由遊戲獨立控制。
8. 製作方式採用「先靜態參考圖，再生成影片」。
9. 先完成 Level 1 技術驗證，再批次製作其餘世界。
10. 以 6 歲兒童的可玩性、辨識度和安全性優先。

## 2. 統一美術風格

### 2.1 主要風格 — CONFIRMED

**Cute Stylized 3D Cartoon Fantasy Adventure**

視覺特色：

- 可愛、圓潤、明亮。
- 卡通 3D 材質與柔和光影。
- 色彩飽和但不刺眼。
- 具有夢幻冒險氣氛。
- 保持遊戲世界的空間感與景深。
- 場景細節主要放在道路兩側與遠景。
- 不同關卡使用共同的造型及光影語言。

禁止風格：

- 寫實攝影、真人實景。
- 低多邊形及明顯的幾何切面。
- 恐怖、陰暗、血腥或壓迫感。
- 過度強烈的鏡頭模糊。
- 頻繁閃爍、強烈頻閃、快速鏡頭旋轉。
- 過度複雜或遮擋道路的環境裝飾。

### 2.2 全關卡一致性

以下屬於所有世界的共同設計語言：

- 固定第一人稱攝影機視角。
- 固定道路透視模型。
- 相同的三線道邏輯。
- 相近的景深與透視強度。
- 統一的卡通 3D 造型和材質品質。
- 一致的動態障礙物合成規範。

以下允許各關不同：

- 色彩主題。
- 道路表面材質。
- 天空、建築、植被與環境。
- 光照氛圍。
- 不影響玩法的裝飾性動態。
- 專屬背景音樂。

### 2.3 世界主題

| 關卡 | 主題 | 主要環境元素 | 視覺情緒 |
|---|---|---|---|
| Level 1 | 陽光草原 | 花田、風車、湖泊、草地、山丘 | 明亮、歡樂 |
| Level 2 | 魔法森林 | 魔法樹木、發光蘑菇、奇幻植物 | 神秘、溫暖 |
| Level 3 | 糖果王國 | 糖果建築、棒棒糖樹、甜點裝飾 | 繽紛、甜美 |
| Level 4 | 未來科技城 | 未來建築、科技道路、霓虹設施 | 活潑、科技 |
| Level 5 | 星際冒險 | 彩色星球、星空、太空道路 | 壯觀、奇幻 |
| Boss | 待確認 | 暫定水晶彩虹城堡 | 最終挑戰 |

五個一般關卡主題為 CONFIRMED。Boss 主題為 DEFAULT，尚未正式定案。

## 3. 攝影機與道路幾何規格

### 3.1 攝影機 — CONFIRMED

所有影片必須使用：

- First-person forward-facing perspective。
- 攝影機沿道路中央向前移動。
- 固定攝影機高度。
- 固定鏡頭俯仰角。
- 固定視角及透視感。
- 不主動轉彎、左右平移或搖晃。
- 不模擬大幅度上下彈跳。
- 不主動縮放或改變焦距。
- 畫面中不出現玩家身體。

鏡頭應營造平穩向前奔跑的感覺，而非真實運動攝影的劇烈晃動。

### 3.2 攝影機參數 — DEFAULT / VALIDATE

初始校正配置：

| 參數 | 暫定值 |
|---|---|
| 畫面比例 | 16:9 |
| 鏡頭水平位置 | 畫面中央 |
| 水平消失點 X | 0.50 |
| 水平消失點 Y | 0.42 |
| 參考水平 FOV | 約 75° |
| 鏡頭 Roll | 0° |
| 鏡頭 Yaw | 沿道路正前方 |
| 攝影機高度 | 固定，數值待校正 |
| 前進速度 | 固定，數值待校正 |

其中 X、Y 使用 normalized screen coordinates，範圍為 0～1，原點位於左上角。

上述 FOV 和消失點只是起始校正值，不代表 AI 影片必然具有精確的相機內參。

**第一個 Level 1 參考圖通過後，應將實際道路幾何參數固定為 Camera Profile v1。**

後續關卡不應各自調整攝影機幾何來遷就畫面。

### 3.3 三線道道路 — CONFIRMED

所有場景必須包含：

- 一條連續向前延伸的主要道路。
- 視覺上分成左、中、右三個區域。
- 道路在近景足夠寬，支援完整的遊戲障礙物。
- 道路通往同一個中央消失點。
- 道路不突然中斷、分岔或轉彎。
- 三線道可透過微弱紋理、材質或色彩區分。
- 不要求使用真實道路的車道線。

三線道主要提供視覺與障礙物定位的共同參考，不代表玩家必須在真實空間移動到三條完全不同的位置。

Dodge 的判定仍由 MediaPipe 的左右跨步動作完成。

### 3.4 道路座標 — DEFAULT / VALIDATE

定義：

- `u`：畫面水平比例。
- `v`：畫面垂直比例。
- `vH`：消失點垂直位置。
- `vB`：畫面底部，值為 1。
- `wNear`：畫面底部的道路半寬。
- `wFar`：消失點附近的道路半寬。

起始建議：

- `vH = 0.42`
- `wNear = 0.46`
- `wFar = 0`

直線道路邊界的簡化投影：

```ts
const t = clamp(
  (v - horizonY) / (1 - horizonY),
  0,
  1,
)

const halfWidth = nearHalfWidth * t

const left = 0.5 - halfWidth
const right = 0.5 + halfWidth

const laneWidth = (right - left) / 3
```

這個公式僅定義初始畫面上的三線道幾何。

實際障礙物縮放、地面接觸點與遠近運動應使用一致的透視投影模型，不能單純假設線性放大就是物理正確的 3D 運動。

影片中的道路必須與這套畫面幾何進行視覺校正。

## 4. 障礙物合成安全區

### 4.1 定義 — CONFIRMED

背景影片的中央道路區域必須保持清楚，提供遊戲生成的障礙物與動作提示使用。

允許裝飾性風景，但不允許出現會讓兒童誤認為需要跳躍、蹲下、左右閃避或擊破的物件。

尤其禁止：

- 道路上的獨立方塊。
- 地面坑洞或裂縫。
- 橫跨道路的橫木。
- 道路封鎖設施。
- 人體輪廓形狀的牆壁。
- 可破壞牆壁。
- 迎面衝來的物件。
- 直接遮擋道路的特效。

上述物件只能由 Canvas / WebGL 產生。

### 4.2 畫面分區 — DEFAULT

以 1920 × 1080 參考畫面為例：

| 區域 | 建議範圍 | 用途 |
|---|---|---|
| 中央核心區 | X 30%～70%，Y 35%～90% | 主要障礙物與姿勢提示 |
| 左側環境區 | X 0%～25% | 植被、建築、景觀 |
| 右側環境區 | X 75%～100% | 植被、建築、景觀 |
| 遠景區 | 地平線附近 | 山丘、天空、遠方建築 |
| 介面保留區 | 實際 UI 決定 | 生命、分數、狀態提示 |

這些比例是保守的起始構圖指引，不是所有障礙物的固定碰撞範圍。

具體的「禁止遮擋區」應根據投影後的三線道、多種障礙物外框、提示輪廓與 UI 共同產生遮罩。

### 4.3 合成限制

- 禁止讓景物假裝穿過 Canvas 障礙物。
- 不在背景影片中預先畫出動態陰影來配合障礙物。
- 障礙物的陰影、碎片及碰撞效果由遊戲生成。
- 背景中的固定環境陰影可以存在。
- 障礙物必須具有清楚的邊界與足夠對比。
- 優先使用簡潔的中遠景環境，而不是高密度動態裝飾。

第一版以一般前景覆蓋合成為主，不要求複雜的影片深度遮擋系統。

## 5. 固定前進速度與同步策略

### 5.1 已確定決策 — CONFIRMED

- 背景影片使用固定的視覺前進速度。
- 一般播放速度維持 `1.0x`。
- 遊戲難度主要透過障礙物間隔、動作組合與複雜度調整。
- 不依賴加速影片來提高遊戲難度。
- 背景影片切換不應改變玩家感受到的跑速。
- 暫停時，影片與遊戲時間軸同步暫停。

### 5.2 重要技術限制

AI 影片是已渲染的影像序列，不提供可靠的真實世界座標、相機內參或每影格位移。

因此：

**無法只靠 Prompt 中的 constant speed，保證背景的實際光流與程式生成的 3D 障礙物完全一致。**

必須以測試影片進行視覺校正。

### 5.3 建議運動模型 — DEFAULT

遊戲為障礙物建立固定的虛擬世界座標和透視投影。

例如：

```ts
interface MotionProfile {
  worldSpeed: number
  obstacleSpawnDistance: number
  cameraFovDeg: number
  horizonY: number
  nearRoadHalfWidth: number
}
```

在固定相機模型中，障礙物沿 Z 軸接近：

```ts
obstacle.z -= profile.worldSpeed * deltaTime
```

再由透視投影計算障礙物的位置和大小。

這裡 `worldSpeed` 使用遊戲內部的虛擬單位，不宣稱與 AI 影片中的真實公尺數相等。

必須避免以不一致的 easing 函式對障礙物尺寸和位置分別進行動畫，導致障礙物看起來漂浮、滑動或加速。

### 5.4 背景校正方式 — VALIDATE

Level 1 首支影片生成後：

1. 抽取多個時間點影格。
2. 檢查道路消失點是否穩定。
3. 檢查道路兩側景物的相對運動。
4. 使用地面紋理、樹木或道路邊緣評估視覺流速。
5. 疊加標準障礙物接近動畫。
6. 調整 Canvas 相機投影與虛擬跑速。
7. 以遊戲實際播放效果確認速度感。

選定參數後建立 `Motion Profile v1`。

後續影片必須盡可能符合這份 Profile，若無法符合則重新生成素材，而不是每支影片各自修改整個遊戲的運動模型。

### 5.5 動態難度

優先調整：

1. 障礙物出現間隔。
2. 可用動作組合。
3. 姿勢複雜度。
4. 安全恢復時間範圍內的挑戰密度。

不將背景速度變化作為主要難度控制機制。

如果未來確實需要調整障礙物接近速度，應另外評估與固定背景的視覺衝突，不能視為已經驗證的功能。

## 6. 模組化影片系統

### 6.1 片段結構 — CONFIRMED

每個關卡可以具有多支背景影片：

- Level 1：草原、花田、風車、湖泊。
- Level 2：魔法樹林、蘑菇森林、發光植物。
- Level 3：糖果街道、甜點村、棒棒糖花園。
- Level 4：科技大道、未來都市、發光設施。
- Level 5：星際道路、彩色星球、太空景觀。

每支影片是可重複利用的景觀片段，不對應固定的障礙順序。

初期每關先製作一支可用影片，成功後再補充多個景觀變體。

### 6.2 長度與格式 — DEFAULT

- 每段影片約 8 秒。
- 16:9 橫向。
- 最終優先使用 MP4 / H.264。
- 以 1920 × 1080 作為正式素材目標。
- 背景影片不保留音軌，或於播放時強制靜音。
- 使用瀏覽器支援的解碼格式，避免不必要的轉碼負擔。

不將 Google Flow 的某個模型、長度或點數費用硬編碼為專案永久限制。

### 6.3 循環策略 — VALIDATE

影片循環不應直接假設無縫。

可用方法依優先順序評估：

**方法一：自然連續循環**

影片結尾與開頭的道路幾何、紋理、運動與光照具有良好的連續性。

**方法二：遮擋式轉場**

利用道路兩側的樹蔭、柔和的霧氣、環境遮擋等過場，降低跳接感。

**方法三：短暫過場特效**

由遊戲程式在安全時機加入短暫的魔法或關卡轉場效果。

**方法四：後製剪輯與交叉淡化**

只有在道路透視及地面紋理適合時才使用，避免產生雙重道路、地面滑動或重影。

相同首尾影格並不代表運動無縫，因此需要檢查接點前後多個影格的運動連續性。

### 6.4 程式切換規則 — CONFIRMED

- 遊戲程式決定目前要播放哪支影片。
- 優先在沒有新障礙物接近的安全時段切換。
- 切換不影響遊戲時間軸與姿態辨識。
- 音樂不因影片片段切換而中斷。
- 切換失敗時可繼續使用目前可用的背景。
- 不得為了切換景觀而讓障礙物突然消失或提前碰撞。

如果素材即將結束卻沒有合適的安全時段，系統必須具備可接受的循環或過場後備策略。

### 6.5 預載策略 — DEFAULT

建議優先使用雙播放器架構：

- `videoA`：目前播放。
- `videoB`：預載下一支。
- 切換後交換角色。
- 使用一個共同的畫面容器，避免切換時尺寸或裁切方式改變。

必須考慮手機記憶體、影片解碼器限制及播放失敗情境。

第一階段可以只使用單支影片循環，等播放與障礙物整合穩定後再增加雙播放器。

## 7. 遊戲事件與視覺回饋

### 7.1 CONFIRMED

背景影片不隨遊戲事件切換到特殊版本。

互動視覺特效由遊戲產生。

| 遊戲事件 | 建議視覺回饋 |
|---|---|
| Jump 成功 | 輕微星光、成功粒子 |
| Duck 成功 | 清楚但不過度的通過回饋 |
| Dodge 成功 | 側向閃避的成功提示 |
| Hole in the Wall 成功 | 姿勢輪廓亮起、通過特效 |
| Smash 成功 | 牆壁碎片、短暫打擊效果 |
| 碰撞失敗 | 柔和畫面邊緣提示 |
| Level Clear | 彩虹、星星、慶祝動畫 |
| Game Over | 溫和的失敗提示 |

特效需避免：

- 劇烈鏡頭晃動。
- 頻繁全畫面閃光。
- 遮擋下一個障礙物。
- 使玩家誤以為需要額外進行動作。

## 8. 音訊規格

### 8.1 CONFIRMED

- 背景影片靜音。
- 音樂由獨立音訊系統播放。
- 不同關卡可使用不同音樂。
- 動作音效由實際遊戲事件觸發。
- 景觀影片切換不影響背景音樂。
- 動作判定不依賴音訊播放時間。
- 暫停時同步處理音樂與音效。
- 音量必須可調整。

初期不要求複雜的環境音系統。

## 9. Google Flow 生成規格

### 9.1 基本流程 — CONFIRMED

1. 撰寫關卡世界觀與劇本。
2. 撰寫場景分鏡。
3. 產生靜態參考圖。
4. 檢查道路與攝影機構圖。
5. 使用 Google Flow 的參考影格生成影片。
6. 下載影片並移除或停用音訊。
7. 進行幾何、視覺速度與循環驗證。
8. 使用 Codex 的測試畫面疊加障礙物。
9. 通過後登記素材 Metadata。
10. 才製作下一支片段。

### 9.2 靜態參考圖規範

每張參考圖必須具備：

- 16:9 畫面。
- 符合共用攝影機 Profile。
- 寬闊且連續的三線道道路。
- 清楚的道路消失點。
- 道路上沒有遊戲障礙物。
- 左右環境能明確表現關卡主題。
- 視覺風格與其他關卡一致。
- 無文字、Logo、水印或遊戲 UI。

未通過參考圖驗收前，不進入影片生成階段。

### 9.3 英文 Prompt 結構

所有 Google Flow 影片 Prompt 應包含以下區塊：

1. **Visual Style**：統一卡通 3D 夢幻風格。
2. **Environment**：關卡專屬景觀。
3. **Road Geometry**：筆直三線道、中央消失點。
4. **Camera**：固定第一人稱向前視角。
5. **Motion**：穩定向前移動、固定速度。
6. **Composition**：中央道路保持乾淨。
7. **Restrictions**：禁止障礙、角色、轉彎等。
8. **Transition Intent**：說明預期循環或銜接方式。

### 9.4 共用影片 Prompt 基底

以下為英文共通 Prompt，實際使用時須另外加入各關環境描述與已核准的靜態參考影格。

```text
Cute stylized 3D cartoon fantasy adventure game environment.

First-person endless runner camera, centered on a wide,
straight, three-lane visual pathway.

Preserve the composition, road perspective, vanishing point,
camera height, and visual identity of the provided
reference image.

The camera moves smoothly forward along the center
of the pathway at a constant visual pace.

Stable forward-facing camera.
No turns, no camera rotation, no lateral movement,
no sudden acceleration, no zoom, no camera shake.

The central pathway remains clear and unobstructed.

Place decorative environmental details mainly
along the sides of the road and in the background.

Bright, cheerful, colorful, child-friendly atmosphere.
Soft lighting, rounded stylized 3D shapes,
consistent cartoon materials.

No characters, no player body, no vehicles,
no gameplay obstacles, no holes, no barriers,
no overhead beams, no walls blocking the road.

No text, no logos, no HUD, no UI.
No dramatic flashes, no sudden scene cuts.

Designed as a reusable background video layer
for a motion-controlled children's running game.
```

注意：

- Prompt 只能提供生成指引，不能保證模型遵守全部幾何限制。
- 無聲影片應由輸出後處理或播放器設定保證。
- 如需首尾影格控制，可針對特定片段加上額外限制。
- 不要求每次生成時都製作專屬首尾影格。

### 9.5 生成成本管理 — DEFAULT

- 先使用可支援參考影格的低成本模式驗證。
- 每次記錄模型、生成長度、Prompt 版本及點數。
- 避免未檢查前一次結果就大量批次生成。
- 當問題來自靜態構圖時，先修正參考圖，不直接反覆重拍影片。
- 優先完成一支可整合素材，再擴充景觀數量。
- 最終解析度與畫質應在手機實測後選擇。

## 10. 素材結構與 Metadata

### 10.1 檔案命名 — DEFAULT

影片：

```text
l01_meadow_001.mp4
l01_meadow_002.mp4
l02_forest_001.mp4
l03_candy_001.mp4
l04_tech_001.mp4
l05_space_001.mp4
boss_001.mp4
```

參考圖：

```text
l01_meadow_001_reference.png
```

生成指令與分鏡使用對應的素材 ID。

### 10.2 Metadata 範例

```json
{
  "id": "l01_meadow_001",
  "level": 1,
  "world": "sunny-meadow",
  "scene": "flower-field",
  "video": "/videos/level-01/l01_meadow_001.mp4",
  "referenceImage": "/references/level-01/l01_meadow_001_reference.png",
  "durationSeconds": 8,
  "aspectRatio": "16:9",
  "cameraProfile": "camera-v1",
  "motionProfile": "motion-v1",
  "loopMode": "pending-validation",
  "hasAudio": false,
  "status": "candidate"
}
```

`camera-v1` 與 `motion-v1` 必須在測試完成後對應到實際存在的 Profile 定義。

`durationSeconds` 代表素材的實際驗證長度，不能永遠假設影片恰好是 8 秒。

素材狀態建議使用：

- `candidate`：尚未驗證。
- `approved`：已通過整合測試。
- `rejected`：存在不可接受的問題。

正式關卡只使用 `approved` 素材。

## 11. Codex 整合要求

### 11.1 模組分工

建議架構：

```text
src/
├── game/
│   ├── GameClock.ts
│   ├── GameState.ts
│   └── DifficultyController.ts
├── video/
│   ├── BackgroundVideoManager.ts
│   ├── VideoPreloader.ts
│   ├── VideoTransitionController.ts
│   └── VideoManifest.ts
├── rendering/
│   ├── CameraProjection.ts
│   ├── RoadCalibrationOverlay.ts
│   ├── ObstacleRenderer.ts
│   └── EffectRenderer.ts
└── config/
    ├── cameraProfile.ts
    ├── motionProfile.ts
    └── levels.ts
```

此為建議模組切分，不要求 Codex 在 Phase 1 就實作所有檔案。

### 11.2 必要行為

**背景影片管理器**

- 載入指定關卡素材。
- 播放與暫停影片。
- 保持固定播放速率。
- 處理影片載入與解碼錯誤。
- 追蹤播放狀態。
- 支援未來擴充不同片段。
- 不得直接控制障礙物判定。

**遊戲時間軸**

- 控制障礙物出現與接近。
- 控制判定時間窗。
- 控制遊戲暫停與恢復。
- 不將影片的 `currentTime` 當成遊戲邏輯時鐘。
- 當遊戲進入暫停狀態時要求影片暫停。

**畫面合成**

- 影片作為背景。
- Canvas / WebGL 作為透明前景。
- 兩者保持相同的視覺座標基準。
- 響應式縮放不能各自採用不同的裁切方式。
- 必須能正確處理手機、平板及橫向畫面。

### 11.3 幾何校正 Overlay

開發階段須能顯示：

- 畫面中心線。
- 道路消失點。
- 道路左右邊界。
- 三線道分界。
- 障礙物合成安全區。
- 標準障礙物接近測試。
- 目前影片 ID。
- 播放時間與狀態。
- FPS 與重要除錯資訊。

校正 Overlay 只用於 Debug，不顯示於正式遊戲。

## 12. 素材與整合驗收

### 12.1 靜態參考圖驗收

必須確認：

- 美術風格正確。
- 無寫實或低多邊形特徵。
- 道路有清楚的三線道空間。
- 道路消失點符合 Camera Profile。
- 畫面中央沒有障礙物。
- 景觀符合指定世界主題。
- 構圖具有足夠的障礙物顯示空間。

### 12.2 影片本身驗收

必須確認：

- 攝影機連續向前運動。
- 沒有突然轉彎、旋轉或加速。
- 道路不明顯變形、分岔或消失。
- 地平線位置沒有明顯漂移。
- 環境元素沒有嚴重變形或突變。
- 沒有意外生成遊戲障礙物。
- 沒有文字、人物、UI 或水印。
- 畫面沒有過度閃爍或劇烈晃動。
- 循環與轉場的品質可接受。

### 12.3 工程整合驗收

必須確認：

- 影片與障礙物使用一致的畫面座標基準。
- 障礙物接地位置合理。
- 障礙物接近動畫沒有明顯滑動。
- 背景與障礙物的速度感相容。
- 影片切換不改變遊戲難度或判定結果。
- 遊戲暫停時影片同步暫停。
- 恢復後障礙物判定時間正常。
- 音樂不因影片切換而中斷。
- 影片載入失敗不會讓遊戲進入無法操作的狀態。
- 手機與平板的播放效能符合可玩需求。

### 12.4 建議量化驗收參數 — VALIDATE

以下只作為第一版測試目標，並非已驗證的標準：

| 指標 | 建議測試目標 |
|---|---|
| 消失點位置漂移 | 不超過畫面寬、高各約 2% |
| 道路與 Overlay 邊界偏差 | 關鍵測試區域內約 3% 以內 |
| 明顯鏡頭加速、轉彎 | 0 次 |
| 非預期玩法障礙物 | 0 個 |
| 可見的突兀場景跳接 | 0 次 |
| 可感知的背景停頓 | 盡可能為 0 |
| 影片與障礙物運動衝突 | 不可有明顯衝突 |
| 素材接點品質 | 實機播放人工驗收 |

如測試發現這些閾值不符合兒童可玩性，應調整驗收參數，而不是為了通過數字測試犧牲實際品質。

### 12.5 驗收狀態

每支影片的正式狀態：

1. Draft：腳本完成。
2. Reference Approved：參考圖通過。
3. Generated：影片已生成。
4. Visual Passed：視覺檢查通過。
5. Integration Passed：遊戲合成通過。
6. Approved：可供正式遊戲使用。

禁止將尚未完成整合驗證的影片標示為 Approved。

## 14. 非目標與風險

本規格不要求：

- AI 直接在影片中生成碰撞障礙。
- 背景影片與動作判定影格精確綁定。
- 為每一個隨機動作生成不同背景影片。
- 所有關卡一次完成影片生成。
- 一開始就建構完整的複雜影片編輯系統。
- AI 影片提供精準的 3D 場景深度與物理座標。

主要風險：

1. AI 影片道路透視不穩定。
2. 背景地面光流與障礙物接近速度不協調。
3. 影片首尾無法自然循環。
4. 多支影片轉場時發生景觀跳接。
5. 行動裝置的影片解碼與 Canvas 渲染競爭資源。
6. 動態裝飾干擾兒童辨識障礙物。

上述風險必須在 Level 1 原型中優先驗證。

## 15. 最終交付原則

後續每一關的製作，都應依照下列順序：

**關卡劇本 → 分鏡 → 靜態參考圖 → Google Flow 生成 → 素材驗收 → Codex 整合 → 實機驗證。**

除非明確提出修改共用規格，否則不應在不同關卡中隨意改變道路透視、攝影機高度或基本前進速度。

**第一個正式里程碑：完成 Level 1 陽光草原的第一支可用背景影片，讓它在遊戲中與即時障礙物正確融合，並通過循環、暫停和行動裝置驗收。**

只有達成這個目標，才能將同一套製作方法擴充至其他世界。

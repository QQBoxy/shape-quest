# 完整 AI 影片轉場 PoC

## 停頓修正（目前版本）

先前版本在 cover/reveal 主動暫停影片並停止更新背景畫布，而且可能等到片尾才得到安全空檔，會出現背景停住、障礙物還在動的問題。舊版120秒結果只證明基本安全與效能，**沒有驗證轉場時背景持續前進**，不應當作連貫性驗收。

另外修正快速重設、暫停或seek取消未完成play()時，誤把正常AbortError判成播放失敗的問題，並加入連續重設回歸測試。

目前改成：影片在 cover、waiting、reveal 全程持續播放；畫布持續接收有效影格。seek／換來源後先確認至少兩張不同 mediaTime 的有效影格，再開始 reveal。轉場進入時是移動的舊場景，離開時是已在播放的新場景。

自動模式提前在片尾前巡查安全空檔，僅當沒有已預告障礙物時，延後尚未預告的下一題與後續題目，保留片尾遮蔽所需時間；距片尾「半段動畫＋0.3秒」開始遮蔽，不再正常播到結束才等待。已預告題目的碰撞時間不改。此調整會讓題目稍微稀疏，正式題數和節奏仍需評估。

若影片意外播完、seek 或超過200ms沒有影格回呼，遊戲時鐘與障礙物一起等待，避免背景停住而障礙物繼續前進。手動關閉自動轉場並播完時，畫面會提示重設，不在已有障礙物時強制遮蔽。

[修正後T2實際播放錄影](transition-tests/motion-fix/T2-motion.webm)約10秒，含兩次轉場，可直接觀看背景與障礙物的連續運動。

最新版量測、實際影格與截圖另存於 `transition-tests/motion-fix/`，保留原始測試供比較。新增自動斷言：cover/reveal 期間影片未暫停、實際提交的背景 mediaTime 前進超過0.1秒、至少增加3張影格；自動循環120秒的片尾停留時間必須為0。這仍不能代替人工判斷轉場自然度。


本頁為獨立技術實驗，不改正式 Game、Renderer、Background 與 MediaPipe 核心，不取代正式方案；保留影片與 B1/B2 PoC、素材和結果。所有效果為 Canvas 程式生成，沒有新套件、後端或付費素材生成。

## 時鐘、安全與播放器

`src/transition.ts` 為獨立轉場狀態機，流程 `idle → pending → cover → waiting → reveal → idle`，失敗停在 `failed`。主頁使用現有 `Game.tick`、`Game.accept`、`Renderer.draw`，不重寫碰撞判定。

1. 距片尾 preview＋半段動畫＋0.5秒開始檢查保留空檔；只在未預告題目時延後下一題。距片尾半段動畫＋0.3秒提出轉場請求（手動可更早）。單播放器保留原片緩衝，沒有假裝第二個來源已解碼。
2. pending 階段正常跑 Game；任何未完成障礙物距離碰撞 ≤ preview + 0.1 秒就延後，不遮住已預告的題目。未清除的逾期障礙物也會阻擋轉場。
3. 安全空檔開始短過場，主機暫停呼叫 Game.tick。已預告的 obstacle collision 時間不動；尚未預告的題目可在事前保留空檔時一起延後，Game Clock 不重設，分數、生命與未出現的障礙物保留。轉場期間不接受方向鍵；不會在看不見時扣血。
4. cover 完成時，T2～T5 先畫不透明底，再將同一播放器 seek 到 0 或換同世界來源。T1 刻意只有注意度抑制，仍不能完整隱藏。
5. waiting 期間保留最後有效畫布與最高遮蔽，直到 requestVideoFrameCallback 確認 seek 完成、readyState ≥ 2、非 seeking，且新 mediaTime < 1 秒，累積至少兩張時間持續前進的有效影格後才 reveal。不以 seeked 或 canplay 單獨判定完成。
6. 舊影片在 cover 繼續播放，新影片在 waiting／reveal 繼續播放，畫布全程更新有效影格；只凍結遊戲判定時鐘。過場不改影片 playbackRate、不加速障礙物。
7. 等待超過 4 個運作秒即凍結遊戲與遮蔽，顯示重試；不自動露出未就緒影片。原有效影格持續保留。重試重新 seek／載入，成功才離開；初始化載入錯誤也可重試。

**片尾與障礙物：** 自動模式事前保留尚未預告題目之間的空檔，在舊影片結束前遮蔽完成。若意外播完，背景和遊戲判定一起保留，不再讓障礙物單獨前進；介面提示重設。手動關閉自動轉場亦採同步保留。未知的密集題型若完全無可預留空檔，應由正式排程在預告前保留過場，不能改掉已預告的題目。

短過場會增加實際經過時間。比較 `activeSeconds`、`gameTime`、`blockedSeconds`，不能把 120 秒測試說成 120 秒純遊戲時間。正式 90～120 秒若指現實時間，需預算過場次數或降低切換頻率；目前是遊戲時鐘有效時間另外加短過場。沒有直接提高 Game Clock 或重排障礙物。

暫停、頁面隱藏與模擬追蹤異常共用運作閘門，凍結 Game／轉場時鐘、等待逾時與播放器。恢復時延續同一時刻，不重設 Game。大於 200ms 的前景卡頓也不跳過判定窗，而是凍結該幀模擬並記錄。追蹤異常只是 adapter 模擬，**並未同時啟動 MediaPipe，也未驗證姿態推論負載**。正式串接需將現有追蹤狀態接入此閘門。

HTML5 media 的 readyState 不等於已呈現新影格；實作參照 [WHATWG media ready states](https://html.spec.whatwg.org/multipage/media.html#ready-states) 與 [WICG requestVideoFrameCallback 說明](https://wicg.github.io/video-rvfc/)。不支援 requestVideoFrameCallback 的瀏覽器明確停用此 PoC，不以 currentTime 假裝成功。

## 單／雙播放器與素材需求

目前只用一個 HTML5 Video，加一張 1280×720 有效影格快取（RGBA 約 3.52 MiB，不含瀏覽器影片解碼緩衝、GPU 複本與畫布）。解碼成本記錄為瀏覽器 processingDuration，不是 CPU 使用率；JS 提交時間不是完整 GPU 時間。沒有量測程序 RSS／GPU 記憶體，不提供虛構記憶體數據。

修正前的六組120秒桌面實測（歷史，非目前版本結果）：T1～T5各13次切換，零逾時、零遮題幀；T0為14次原生循環。T2新影格等待P95約118ms，T1／T3／T4／T5約35～36ms，RAF約59.5～60。這些數字支持目前PoC維持單播放器，尚未支持手機也足夠的結論。瀏覽器回報的解碼 processingDuration P95 約250ms，是提交到可解碼的處理區間，並非每一幀花250ms的CPU耗用或畫面必然停頓；應與約60FPS、回呼間隔與真正切換等待一起判讀。

先以量測等待時間與人工觀察決定單播放器是否足夠。若行動裝置換來源／seek 的 P95 持續超過預設過場預算，或常有大於 0.5 秒額外停留，再評估雙播放器預載；不要把桌面結果推論成手機結果。第二播放器會增加壓縮緩衝與解碼表面、可能同時佔用兩個硬體解碼通道，行動瀏覽器背景播放器也可能被節流／停播。需 iOS Safari、Android Chrome 實測播放限制與峰值記憶體，再決定是否常駐雙解碼。

現有 PoC 不需要任何新素材。正式 T2 建議透明帶陰影的 3D 雲團圖集／可循環短片，T3 建議柔和門框及無障礙語意標記，T5 建議糖紙／巨型糖果前景透明圖層；透明素材必須與實色底搭配。可以委託美術或另製素材，本次未呼叫付費 AI。T4 可完全程式化，但與影片美術協調仍需人工調色。

## 驗收界線與待辦

桌面測試可確認持續時間、錯誤、等待、時鐘／暫停、障礙物安全指標與新影格門檻；`missingFrameRenders = 0` 只代表有有效來源可畫，**不是逐像素黑畫面檢測**，也不是影片本身沒有黑幀的證明。本 PoC 不混合前後兩張影片，所以不引入交叉淡化雙影，但 T1 blur 本身可能模糊景物。

必須人工觀看每個方案的實際影格帶，並在操作頁連續觀看；不能用 FPS 或自動化通過宣稱自然。尚待：原片接點與不同片段的視覺瞬移判讀、逐幀黑畫面與停頓檢查、最終3D素材評審、兒童舒適度與門／糖果語意測試、手機和平板實機、MediaPipe 同時推論、電視鏡像延遲／幀率與動作判定測試。這些未執行項目不得標成已通過。
